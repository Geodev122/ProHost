# Integration audit — Phase P2 (de-Android the app in place)

Scope: database ↔ backend ↔ frontend ↔ admin web, after P2.1–P2.5 (build cleanup, context-free view models, dates/ids/number formats, `PickedFile`, UI seams: platform actions, pickers, location, geocoding, sounds). Method: `integration-audit` skill; mechanical checks below were run on branch `claude/sharp-clarke-w4rlh2`.

## What P2 changed outside `app/`
`git diff <merge-base with main>..HEAD -- functions firestore.rules storage.rules tests firebase.json public`:

| File | Change | Effect |
|---|---|---|
| `functions/src/bookings/bookingTerms.ts` (+ test) | month addition clamps to the last day of the month (owner request, plan §13) | server end date for bookings starting on the 29th–31st moves 1–3 days earlier, now equal to the app; **goes live only when merged to `main`**; no data migration (terms computed on read) |

| `firestore.rules`, `storage.rules`, `firebase.json`, `public/` | **no change** | — |

No callable, collection, field, rule or Storage path was added, removed or renamed by P2.

## Checks
1. **Callables ↔ exports.** All 30 callable names the Android client uses (`FirebaseFunctionsClient` and any other `getHttpsCallable`) exist as server exports (87 exports found). Missing on server: none.
2. **Client Firestore collections ↔ rules.** Collections the client names (`booking_occupancy`, `user_profiles`, `versions`, and the constants `audit_security_logs`, `booking_requests`, `legal_documents`, `system_metadata`, `workspace_listings`): each has a `match` in `firestore.rules` (the `versions` subcollection sits under `legal_documents`).
3. **Rules ↔ rules tests.** `audit_security_logs`, `legal_documents` and `system_metadata` have no mention in `tests/rules`. They are admin-only collections; P2 did not touch them. **Finding F1 (pre-existing):** add positive/negative admin cases before P1.F (already planned in P1.4; no behaviour change).
4. **Storage paths ↔ `storage.rules`.** Rules cover `/profile_pictures/`, `/listing_verification_docs/`, `/booking_agreements/`, `/listings/`, `/legal_documents/` and `/b/`. P2 moved only the *type* of the picked file (`PickedFile` instead of `Uri`); upload paths and content types are unchanged (`FirebaseStorageService`, equivalence tests in `PickedFileAccessTest`).
5. **Mirrored logic ↔ shared vectors.** Booking terms, legacy pricing and listing prices run from the same JSON in `node --test` and Kotlin (`VectorsTest`); the month-end divergence found in P0 is resolved on the server side. Attendee pricing and price change keep their shared cases (unchanged by P2).
6. **Dates.** All non-admin date code uses `IsoDate`/`BookingDates`/`MonthBoundaries` (kotlinx-datetime), proven equivalent to the old `Calendar` code on every JDK zone; billing dates deliberately stay on `Calendar` (owner decision, `BillingDatesCharacterizationTest`).
7. **Data model doc.** `docs/DATA_MODEL.md` unaffected: no field or collection changed.
8. **E2E flows (`tests/e2e/flows.test.js`).** Run in CI only (the sandbox proxies localhost); the bookingTerms change is exercised by the conflict-guard flow when merged to `main` (deploy gate). Not dispatched from the branch.
9. **Admin web.** Android admin code untouched (owner rule); web console work is a separate track (P1).

## Result
No integration drift introduced by P2. One pre-existing gap (F1, admin collections without rules tests) carried into P1.4. One deliberate server change (month-end clamp) waits for merge to `main`.
