### P2.3a follow-up: core-library desugaring (found while learning P2.3c)
- **Finding:** `kotlinx-datetime` on Android wraps `java.time`, which exists natively only from API 26; the app's `minSdk` is **24** and had no desugaring, so `IsoDate` would have thrown `NoClassDefFoundError` on API 24-25 devices. The Parity Gate cannot see this (Robolectric runs at SDK 34, unit tests on a modern JVM). **Fix:** `isCoreLibraryDesugaringEnabled = true` + `coreLibraryDesugaring(desugar_jdk_libs 2.1.5)`; the R8 release step of the gate proves the build still shrinks. **Rule for later steps:** any new `java.time`-backed API (kotlinx-datetime) is only safe because desugaring is on; keep it on while `minSdk < 26`. A real check on an API 24/25 emulator belongs to the internal-testing smoke (owner/CI follow-up in P2 gate).

### P2.3c Billing dates: NOT ported (decision from evidence) — `PlayOfferText.regularPriceStartsAt`, `PlayPromo.endOfDayBeirut`
- **What happened:** the port to kotlinx-datetime was written and tested against the old `Calendar` code (8 time zones, 87,600 + 2,976 cases). Gate run 42507779609 failed exactly those two new tests; everything else (433 tests) passed. Reproducing both implementations on the JDK (`java.time` is what kotlinx-datetime wraps) shows a **real one-hour difference in clock-change overlaps**: `Calendar` resolves a repeated wall-clock time to the LATER (standard-time) occurrence, `java.time` to the EARLIER. `endOfDayBeirut`: 8 of 2,976 dates differ, always the Saturday before Beirut's clocks go back (e.g. `ends-20261024`: a port ends the promo an hour early); `regularPriceStartsAt`: 4 of 87,600 cases (Europe/Berlin, result in the repeated 02:xx hour).
- **Decision (no behaviour change):** revert the port. These two functions live in Android-only billing code (Play Billing types) and only become shared with the common offer model in P5, so nothing is gained now. `BillingDatesCharacterizationTest` pins the current behaviour, edge cases included (values verified on the JDK: 20261024 → 1792879199000; Berlin 2026-07-25 02:02:03 + 3 months → 2026-10-25T01:02:03.456Z), as the spec the P5 port must reproduce (resolve an overlap to the later offset explicitly).
- **Rule learned for all remaining date work (P2.3d+):** any function whose result is a *time of day* in a DST zone can differ by one hour from `Calendar` in an overlap; date-only functions (ISO strings, UTC) are safe. Equivalence tests must include overlap/gap days in zones with midnight transitions (Beirut) and must be reproduced on the JDK before porting.
